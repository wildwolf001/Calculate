# 2026-11-11 修复记录：口径治理、泛化与边界

> 关联：`design/PROJECT_MAP.md`、`design/REFACTOR_STATUS.md`
> 范围：`app/datasets`、`app/domain/semantic`、`app/api`、`app/ingest`、`app/core`、`tests/`

本次修复针对三个问题的实测结论：语义层多副本互相打架、发布动作破坏 provenance、新领域数据没有端到端验证。下面每条都写清楚"改了什么、为什么、怎么验证"。

## 1. 发布不再重写 provenance

**问题**：`publish.py` 把每个保留指标的 `provenance` 强制改成 `human`。于是 `merge.py`（只保留 `human` / `documentation`）在重建时会把一次发布过的**机器草稿**当成人工口径永久恢复；数据或文档变了也不会更新。

**改动**：

- `app/datasets/publish.py`：保留原始 `provenance`，新增 `confirmed_at` / `confirmed_by="publish"`。
- `app/api/routes.py`：人工编辑指标/维度时写入 `provenance="human"` 与 `edited_at`。
- `app/datasets/merge.py`：保留集合仍是 `{human, documentation}`，注释明确"发布不是作者"。

**验证**：发布一个数据集后检查 `semantic.yaml`，`provenance` 分布应保留 `auto/model/documentation`，仅被人工编辑的对象为 `human`。

## 2. supported_grain 与能力图谱单一来源

**问题**：同一指标的可分组维度有两份声明——YAML 的 `supported_grain` 与 `graph.build_capabilities()` 的推导结果。planner/validator 信任图谱，merge/validate 信任 YAML，同一个问题会得到两种答案。

**改动**：`publish.py` 在写 YAML 前用 join 图计算一次能力，把 `allowed_dimensions ∩ 已发布维度` 写回每个指标的 `supported_grain`（`none` 恒在首位）。后续 readiness / capabilities.json / semantic_index.json 复用同一份结果，不再二次推导。

**取舍**：发布时以能力图谱为准，YAML 里旧的人工白名单会被覆盖。需要限制指标可分组范围的场景，应使用 `filter_grain` 或后续新增的 `restricted_dimensions`，而不是手改 `supported_grain`。

## 3. 同名维度按指标换用安全副本 + 默认时间轴

**问题**：9 张表合并后，`订单状态` ×4、`客户城市` ×4、`客户省份` ×4 是同一业务概念的逐事实表副本。用户问"按订单状态"，解析器可能选中当前指标不可用的副本，于是被降级或拒答。

**改动**：

- `app/domain/semantic/graph.py` 新增 `same_name_dimension()`：在指标允许的维度里找唯一同名副本。
- `app/domain/capability.py`：先尝试换用同名副本（`action="replace"`），仍不行才降级/拒答；`apply_degradations()` 支持替换。
- `app/domain/planner.py`：`degrade_unsupported_dimensions()` 同样先换用，再降级，事件里记录换用了哪个维度。
- `app/datasets/publish.py`：写出 `dimension_groups`（同名维度分组）与每个指标的 `default_time_axis`（未指定时间轴时以指标自身事件时间为准）。

## 4. 索引与语义层版本校验

**问题**：`semantic_index.json` 只在发布时生成；`PATCH /datasets/{id}/draft` 改完 YAML 不会重建索引，解析器会拿到改名前的 brief。旧索引本身也没有内容指纹。

**改动**：

- `app/datasets/index.py`：新增 `semantic_fingerprint()`，写入索引。
- `app/datasets/context.py`：加载时校验指纹；指纹缺失时退回比较 `semantic_version`；不匹配则丢弃索引（解析器退回 schema card），绝不用过期索引提示模型。
- `app/api/routes.py`、`app/api/uploads.py`：draft 编辑、口径文档应用后重建索引（best effort，不阻断主流程）。

- **预测类拒绝**：`能预测下个月卖多少吗？` 不再走“没有识别出「预测（未来值外推）」”的通用词面兜底。Controller 在解析前识别预测/利润类越界问题，直接说明“只有历史交易、没有预测模型/成本字段”，并给中文历史基线选项；不再出现 `price`、`freight_value` 这类英文列名。

- **内部错误**：`_multi_interpretation_events` 原先只捕获 `PipelineError`；某个模型解释在 `prepare()` 抛出 `SemanticError` 时整轮变成 `INTERNAL_ERROR`（Turn 11 “一共卖了多少？”）。现在按单个解释捕获异常、记录 `interpretation.rejected` 并继续，其他有效解释仍能回答。
- **模糊分析**：`卖得怎么样？` 被解析为 `analysis` 后会直接跑 12 个查询的完整报告。现在 `_is_vague_analysis` 先判断是否只是模糊的经营问题；没有“分析/报告/诊断/复盘”等明确指令时，返回范围澄清（趋势/最近一月/品类城市/体验指标），不生成整份报告。
- **通用未识别文案**：`「X」不是当前数据源的指标或维度。` + 解释“可能是业务概念/计算口径/外部数据”，不再重复“数据里没有…这个指标或字段”；列候选只使用中文描述，避免把英文物理列名当示例问题。

**验证**：
- 新增 `tests/integration/test_session_2ff8b7.py`（4 项）：预测拒绝、利润拒绝、模糊分析澄清、坏解释不拖垮整轮。
- 全量：`340 tests / 0 failed / 104 skipped`。
